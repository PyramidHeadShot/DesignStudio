# Лимиты изображений в контексте LLM-запросов

Практика, вынутая из реального отказа сессии 2026-09-26
(`.pi/sessions/2026-09-26T05-24-00-925Z_*.jsonl`, провайдер `provod`,
модель `mimo-v2.6-pro`). Всё проверено экспериментом, не теория.

## 0. Симптомы (как узнать, что это именно оно)

1. Сессия отвечала нормально, потом **резко и навсегда** начала падать.
2. Каждый ответ ассистента — пустой, `stopReason: "error"`, в логе:
   ```
   400: {"code":"INVALID_REQUEST","message":"The model could not process this
   request. Check its parameters and content.","param":null,
   "type":"invalid_request_error"}
   ```
3. Ответ приходит **мгновенно** (~30–90 мс) — запрос отклонён до генерации.
4. В `usage` — нули: **деньги не списываются**, залипшие запросы бесплатны.
5. Помогает НИЧТО из диалога: «продолжи», «1», новая короткая команда — история
   с картинками уезжает в каждом запросе, 400 повторяется.
6. Перед отказом активно использовались vision-инструменты: скриншоты
   (`chrome-devtools_take_screenshot`, особенно с `includeSnapshot`),
   `read` картинок, аудиты со скриншотами.

## 1. Быстрая диагностика jsonl-сессии

```bash
S=.pi/sessions/<файл>.jsonl

# 1) Когда начались ошибки (первая строка с error):
grep -n 'stopReason":"error' $S | head

# 2) Сколько изображений накопилось и где:
python .agents/skills/image-context-limits/scripts/inspect_session.py $S
```

`inspect_session.py` показывает для каждой картинки: строку jsonl,
размер base64, валидность PNG (сигнатура + IEND), пиксели из IHDR
(!!! vision-токены считаются по пикселям, не по байтам), md5-дубликаты
и суммарный «визуальный вес» истории. Дубликаты — норма: так работает
`includeSnapshot` и повторные `take_screenshot` при неизменной странице.

Частые второпричины, которые скрипт тоже покажет:

- картинки 1920×934 и крупнее — у vision-моделей лимит и по токенам/пикселям;
- у модели **нет `inputLimits.images.resize`** — изображения кладутся в
  историю как есть (полные 1920×863+), вместо сжатия до 1568×1568/JPEG q75;
- обрезанный PNG (нет IEND) — тогда 400 бывает и на одной картинке.

## 2. Поиск лимита провайдера (воспроизведение)

Ошибка воспроизводится **одним запросом** с картинками из той же сессии —
это бесплатно (отказ до генерации) и точно локализует причину:

```bash
python .agents/skills/image-context-limits/scripts/probe_image_limit.py \
    --session .pi/sessions/<файл>.jsonl --model mimo-v2.6-pro --provider provod
```

Скрипт берёт реальные PNG из истории и находит границу «N картинок — 200,
N+1 — 400». Тот же скрипт используй для проверки любого нового провайдера/модели.

### Проверенные лимиты (добавляй по мере замеров)

| Провайдер / модель | Изображений на запрос | Примечание |
|---|---|---|
| `provod` / `mimo-v2.6-pro` | **4** (5 → 400) | замерено 2026-09-26, бинарный перебор |
| `provod` / `glm-5.3-flash` | не замерено | есть `inputLimits.images.resize` |
| ~~polza~~ / `glm-5.3-flash` | — (провайдер удалён, полный переход на provod) | — |
| `ollama` / qwen3* | не замерено | без vision по конфигу |

Лимит — на **каждый запрос**, а не на сообщение: вся история целиком
участвует. Поэтому 4 безопасных скриншота в прошлом = 4 «слота» заняты
навсегда, пока сессию не почистят.

## 3. Лечение зависшей сессии

Историю нельзя «переспросить» — её надо физически полегчать. Заменить
base64 старых картинок на текстовый плейсхолдер (бэкап делается автоматически):

```bash
python .agents/skills/image-context-limits/scripts/strip_history_images.py \
    .pi/sessions/<файл>.jsonl --keep 2
```

- `--keep N` — оставить N последних изображений (0 — убрать все).
- Скрипт идемпотентен, можно запускать повторно.
- После запуска — продолжить ту же сессию: она снова заработает.
- Альтернатива, если копия контекста не нужна: `/compact` (но компакция тоже
  отправляет запрос с текущей историей — см. п.4!) или новая сессия.

**Никогда не редактируй jsonl голым текстом** — это JSONL с base64", кривая
правка убьёт парсер сессии. Только скриптом, только с бэкапом.

## 4. Профилактика (главное — поведенческое!)

`inputLimits` в `models.json` — **справочная** подсказка для pi. По доке pi
(`docs/models.md`): каталог может описать `inputLimits.maxRequestBytes`,
`images.maxPerMessage`, `images.maxPerRequest`, но «Pi does not yet rewrite or
reject history based on them» — **историю по ним pi НЕ обрезает**. Т.е.
конфиг не спасает от 400, лимит держится дисциплиной сессии.

Правила работы со скриншотами в длинных сессиях:

1. **Не копи скриншоты.** Каждый снимок живёт в истории до конца сессии.
   Один `take_screenshot` = минус один слот из лимита провайдера.
2. **`includeSnapshot` — зло.** Он дублирует снимок (клик возвращает и текст
   снапшота, и ту же картинку). Анализируй скриншот по необходимости, кликай
   без него.
3. **Считай слоты.** При модели с лимитом 4: заходя в сессию, где уже 3+
   картинки, новые скриншоты почти гарантированно её убьют. Сначала `strip`.
4. **Серию снимков разбивай** на несколько коротких сессий или стрипай
   промежуточные снимки сразу после использования.
5. **2 снимка — рабочий бюджет** длинной сессии: последний кадр + запасной.
6. Прежде чем «просто глянуть скриншот» — подумай, даст ли `take_snapshot`
   (текстовый a11y-снапшот, БЕЗ картинки) достаточно информации. Почти всегда да.

Рекомендуемая конфигурация `models.json` для vision-моделей (где её нет —
добавить; где есть resize — сверить):

```json
{
  "id": "mimo-v2.6-pro",
  "contextWindow": 1048576,
  "maxTokens": 8192,
  "input": ["text", "image"],
  "inputLimits": {
    "images": {
      "maxPerRequest": 4,
      "maxPerMessage": 4,
      "resize": { "maxWidth": 1568, "maxHeight": 1568, "maxBytes": 524288, "jpegQuality": 75 }
    }
  }
}
```

`resize` pi применяет реально (кодирует новые картинки один раз при
поступлении); `maxPerRequest` — только документируй, пока pi не научится
обрезать (проверяй `docs/models.md` — место цитаты выше могло измениться).
Конфиги pi: `~/.pi/agent/models.json`, `~/.pi/agent/settings.json`.

## 5. Чек-лист при внезапной смерти сессии

1. `tail` jsonl — цель: `stopReason:"error"` + текст `errorMessage`.
2. `inspect_session.py` — посчитать картинки, найти первую ошибку по строке.
3. Если картинок у лимита (часто 4–6) — это оно. Подтверждение: до первой
   ошибки стоит toolResult со скриншотом/картинкой.
4. Проверить провайдера/модель на лимит — `probe_image_limit.py`, занести в
   таблицу п.2.
5. `strip_history_images.py --keep 2` → продолжить сессию.
6. Если strip не помог: подозрение на битый PNG или другой контент —
   `inspect_session.py` покажет невалидные; убрать `--keep 0`.
7. Если и это не помогло: упростить историю до минимального префикса, обрезав
   мусорные toolResult осторожно (или начать новую сессию со сводки).

## 6. Связанные подводные камни

- Одинаковые картинки (md5 совпадают) — это НЕ ошибка, а повторный снимок
  неизменной страницы. Но лимит считает их как разные слоты — дубликаты
  можно безжалостно стрипать.
- `stopReason:"aborted"` — не путать с лимитом: это прерванный запрос (Ctrl+C /
  новое сообщение), деньги за него тоже не списываются.
- Если 400 начался СРАЗУ после успеха и картинок мало — проверь размер тела
  (лимит `inputLimits.maxRequestBytes` у провайдера) и `tool_call_id`-парность
  toolCall/toolResult (сломанная пара тоже даёт мгновенный 400). Обе проверки
  — в `inspect_session.py` (секция парности — по `parentId`-цепочке).
