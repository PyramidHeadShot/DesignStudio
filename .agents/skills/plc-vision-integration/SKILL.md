# PLC + Камеры: правила интеграции CV-системы (универсальные)

Контекст: обмен по snap7 (PUT/GET), камеры USB DirectShow / IP RTSP /
industrial GenICam. Всё ниже — реальные баги и их решения, найденные на
живых объектах при тестах обрыва кабеля, отключения питания и гонок
потоков. Не теория.

## 0. С ЧЕГО НАЧАТЬ (порядок работ)

1. Согласовать с программистом PLC **карту сигналов и адреса** ДО кода
   (см. раздел 1 — домены записи).
2. Написать **инструкцию для программиста PLC** (раздел 9) — обязательный
   артефакт, смежник читает её, а не твой код.
3. Реализовать обмен + **эмулятор** (раздел 2) — отладка без контроллера.
4. Тесты логики без железа (раздел 10).
5. Живой прогон по чек-листу (раздел 11).

## 1. ПРОЕКТИРОВАНИЕ ПРОТОКОЛА: домены записи (КРИТИЧНО)

### 1.1. PUT/GET пишет БАЙТ целиком → один байт = один писатель

Запись бита из Python — это read-modify-write байта (прочитал байт,
изменил бит, записал обратно). Если два субъекта пишут биты ОДНОГО байта —
гонка потерянного обновления: PLC изменил свой бит между твоим read и write —
ты записал байт со СТАРЫМ значением его бита.

**Правило: каждый байт имеет ровно одного писателя.**

```
Байт 0  — пишет ТОЛЬКО CV   (DONE, ERROR, ...)     — PLC только читает
Байт 1  — пишет ТОЛЬКО PLC  (TRIGGER, ...)         — CV только читает
Байт 2  — пишет ТОЛЬКО CV   (WATCHDOG)             — PLC только читает
Байт 3  — пишет ТОЛЬКО CV   (OFFLINE)              — PLC только читает
Байты 4-7 — пишет ТОЛЬКО CV (RESULT REAL)        — PLC только читает
```

Если по заданию один байт неизбежно делится — read-modify-write под локом
И документированный запрет PLC-программе писать в этот байт. Лучше —
разнести по байтам.

### 1.2. Типовой handshake-протокол (цикл на одну деталь/измерение)

```
PLC:  TRIGGER = 1  ─────────►  CV: выполняет измерение
                               CV: RESULT = измеренное значение (REAL)
                               CV: DONE = 1, ERROR = 0 (успех)
                                  или ERROR = 1 (не удалось)
PLC:  читает RESULT (ERROR проверить ДО использования!) 
PLC:  TRIGGER = 0  ─────────►  CV: DONE = 0, ERROR = 0 — готов к новому циклу
```

Правила handshake:
- TRIGGER держать = 1 до появления DONE (не импульсить — CV опрашивает
  с периодом 100 мс, короткий импульс будет пропущен);
- TRIGGER сбросить = подтверждение чтения результата;
- новый TRIGGER=1 подавать только после DONE=0;
- при TRIGGER без камеры/данных CV отвечает DONE=1 + ERROR=1 — PLC
  обязан проверить ERROR ДО использования результата;
- новое измерение недействительно, пока не подтверждено отсутствие ERROR.

### 1.3. Карта сигналов — фиксируется в инструкции (раздел 9)

Для каждого сигнала: адрес (byte.bit), направление, тип (BOOL/REAL),
кто пишет, семантика, поведение при аварии/выключении.

### 1.4. RESULT — REAL (IEEE 754 big-endian, стандарт S7)

```python
from snap7.util import set_real, get_real
data = bytearray(4)
set_real(data, 0, value)          # запись
value = get_real(data, 0)         # чтение
# или без snap7: struct.pack('>f', value) / struct.unpack('>f', ...)
```

При выключении системы RESULT обнулять (см. раздел 6) — устаревший
результат после рестарта опаснее отсутствия результата.

### 1.5. Подключение

- PUT/GET на CPU должен быть разрешён (TIA Portal → Свойства CPU →
  Защита и подключение → «Разрешить доступ с PUT/GET»). Частая причина
  «подключение отклоняется».
- DB — только НЕ оптимизированный (standard access), иначе PUT/GET не работает.
- Rack/Slot: S7-1200/1500 — 0/0 (бывает 0/1); S7-300/ET200S — 0/2.
  Согласовать с программистом PLC.
- Для проверки без контроллера — эмулятор (раздел 2).

## 2. ЭМУЛЯТОР PLC — без внешних программ

**Не ищи эмуляторы на GitHub.** В `python-snap7` уже есть сервер:

```python
import snap7
from snap7.server import Server
from snap7.type import SrvArea

mem = bytearray(64)                    # M-память (Merker) 64 байта
server = Server()
server.register_area(SrvArea.MK, 0, mem)   # MK = M-память; DB — SrvArea.DB
server.start_to("127.0.0.1", 102)      # порт 102 на Windows — без админа
```

Клиент подключается штатно: `Client().connect("127.0.0.1", rack, slot)`.
Запись клиента видна в буфере `mem` напрямую (буфер передаётся по ссылке).

Подводные камни:
- `snap7.types` НЕ существует — `SrvArea` ищи в `snap7.type` (без s).
- Строка `Expected COTP DT, got 0x80` в логе — безвредный шум handshake.
- Порт 102: если по сети доступен РЕАЛЬНЫЙ контроллер — эмулятор на 102
  создаст путаницу «к чему подключена система». На время теста отключай.
- Режимы эмулятора: GUI (индикаторы + кнопка триггера), --auto (автоцикл:
  сам подаёт триггер, ждёт результат, снимает триггер, повторяет), --watch
  (read-only монитор). Автоцикл — лучший способ проверить цикл целиком.
- ⚠️ Тест-парадокс: пока эмулятор запущен, он занимает порт 102 —
  интеграционные тесты, поднимающие СВОЙ сервер, должны детектировать
  чужой сервер (canary-запись: записать бит и прочитать его тем же
  клиентом; не совпало — чужой сервер) и корректно скипаться.

## 3. WATCHDOG — пульс жизни (обязательный fail-safe)

**Назначение:** CV-система инвертирует бит каждую секунду — PLC видит,
что программа жива. Без watchdog PLC не отличит «систему видит зону»
от «систему зависла и показывает замёрзший кадр».

### Со стороны CV:
- **Отдельный поток.** Пульс должен продолжаться и во время детекции
  (2-5 сек) — если пульсирует тот же поток, что делает измерение, PLC
  решит, что система зависла. Никогда не пульсируй из потока детекции.
- Инверсия строго по периоду (настраиваемо, `watchdog_period_ms = 1000`);
  писать бит только при СМЕНЕ значения (не каждый цикл).
- При штатном выключении: записать WATCHDOG = 0 и остановить пульс
  (см. раздел 6 — зомби-защита).

### Со стороны PLC (требование к программисту, в инструкцию):
- сравнивать бит со значением 3-5 сек назад;
- не менялся дольше 5 сек → авария «Система CV потеряна» — реакция как
  на отказ датчика;
- «штатное выключение» CV: все биты = 0 и пульс стоп — PLC отличает это
  от «краша» (биты замерли в СЛУЧАЙНЫХ значениях).

## 4. OFFLINE — потеря камеры/источника (зона слепая)

**Семантика (инвертная, fail-safe):** 0 = источник потерян (зона слепая),
1 = связь есть. При обрыве линии/краше PC бит уйдёт или замрёт в «0» —
аварийное значение.

- Пишется при ИЗМЕНЕНИИ состояния камеры (потеря/восстановление), не
  каждый цикл.
- При старте CV пишет актуальное состояние (камеры нет на старте — 0).
- Если OFFLINE = 0: подавать TRIGGER бессмысленно — CV ответит
  DONE=1 + ERROR=1 («измерить не удалось»).
- TRIGGER при OFFLINE=0 НЕ блокируется молча — CV обязан ответить
  ошибкой, чтобы PLC-цикл завершился (иначе PLC зависнет в ожидании DONE).

---

## 5. ERROR — семантика ошибки измерения

DONE=1 + ERROR=1 означает: «цикл завершён, результат НЕДОВЕРИТелен».
ERROR=1 выставляется при: нет объекта измерения / недостаточно опорных
точек / камера потеряна / кадр устарел / исключение обработки.
RESULT при ERROR обнулять (0.0) — PLC не должен читать устаревшее число.

Проверка PLC: **сначала ERROR, потом результат** — иначе первый попавшийся
угол уедет в техпроцесс.

## 6. ЗАКРЫТИЕ ПРОГРАММЫ: обнуление ВСЕГО + зомби-защита

Штатное выключение: ВСЕ сигналы = 0 (включая RESULT/ANGLE!) и стоп пульса.
PLC-программа различает:
- «штатное выключение» — все биты = 0, пульс не возобновляется;
- «краш» — биты замерли в случайных значениях, пульс остановился
  на произвольном значении.

**Зомби-защита (критичный баг 2026-09-16):** фоновый поток, не успевший
завершиться, ПОСЛЕ обнуления перезаписал нули старыми значениями
(реконнект watchdog вернул бит в 1). Решение:

```python
# В клиенте:
self._closed = False

def close_client(self):
    """Финальное обнуление сделано, клиент закрыт — зомби-операции запрещены."""
    self._closed = True
    self.disconnect()

# Guard в начале каждого read/write/reconnect:
if self._closed:
    return None / False
```

Порядок закрытия:
1. `stop_event.set()` для всех фоновых потоков;
2. `join(timeout)` каждого потока;
3. **из ГЛАВНОГО потока** (после join): обнулить ВСЕ сигналы →
   `close_client()` → disconnect;
4. потоки-демоны, не уложившиеся в join, при выходе упрутся в `_closed`
   и ничего не перезапишут.

## 7. КАМЕРЫ: потеря сигнала и реконнект

### 7.1. Отключённая USB-камера НЕ всегда даёт ошибку read()
Главный баг (стоил дня отладки): DirectShow при выдёргивании USB
продолжает отдавать ОДНОТОННО-ЧЁРНЫЕ кадры (ret=True). Детектор честно
обрабатывал чёрные кадры: индикатор зелёный, реконнект не запускался,
на экране застывшая картинка.

Решение — video loss detection (как в промышленных NVR):

```python
def is_signal_loss(frame) -> bool:
    small = cv2.resize(frame, (64, 64), interpolation=cv2.INTER_AREA)
    gray = cv2.cvtColor(small, cv2.COLOR_BGR2GRAY)
    return bool(gray.std() < 3.0 and gray.mean() < 25.0)   # ← bool() обязателен
```

Счётчик ПОДРЯД идущих чёрных кадров >= 12 (~1.3 сек при 9 fps) → потеря
сигнала. Трейд-офф: однотонная тёмная сцена (закрытый объектив) = потеря —
так же делают NVR. Тёмная НО структурная сцена (пятна, полосы) проходит.
⚠️ Чистый random-шум ПОСЛЕ downscale усредняется (std падает в sqrt раз)
и ложно выглядит как потеря — тестируй на структурированном кадре.

⚠️ `np.True_ is True` даёт False — детектор возвращай как `bool(...)`.

### 7.2. ЕДИНЫЙ критерий потери — по ВРЕМЕНИ без свежего кадра
Разные камеры проявляют обрыв по-разному: read() = False (RTSP/мертвый
handle), ЧЁРНЫЕ кадры с ret=True (USB DirectShow), зависание сенсора.
Один критерий на все случаи: **нет свежего (сохранённого) кадра дольше
LOSS_AFTER_SEC (2-3 сек) → потеря**. Свежесть = время последнего
сохранённого кадра (`last_frame_time`), а не время чтения.

### 7.3. Реконнект — БЕСКОНЕЧНЫЙ цикл с backoff (промышленный режим)
Критичный баг: после N неудачных попыток поток умирал (break) —
вернувшуюся камеру некому подхватить, нужен перезапуск программы.
Для промышленной системы недопустимо.

```python
def _reconnect_loop(self):
    while not self.stop_event.is_set():
        if self._try_reconnect():          # release + reopen + верификация
            ...выход из loss mode...
            return
        self.stop_event.wait(self.reconnect_delay)  # backoff: 2→4→8→16→30 сек
```

**Backoff обязателен:** пауза между попытками растёт (2→4→8→16→30 сек).
Причина: камера после подачи питания инициализируется 3-5 сек; попытки
пересоздания каждые 2 сек КОСЯТ её в момент старта — она никогда не
выйдет на режим (баг 2026-09-19: цикл «переподключена, но кадры не идут»).

### 7.4. Верификация реконнекта — по ПЕРВОМУ НАСТОЯЩЕМУ КАДРУ
«Камера открылась» ≠ «камера стримит». DirectShow может отдать 1-2
КАШИРОВАННЫХ кадра (старая сцена) и замолчать. После открытия жди
НЕПРЕРЫВНЫЙ поток ≥2 сек (разрыв > 0.5 сек — отсчёт заново):

```python
def wait_first_frame(cap, timeout=6.0) -> bool:
    deadline = time.monotonic() + timeout
    stream_start = None
    while time.monotonic() < deadline:
        try: ret, frame = cap.read()
        except Exception: return False
        now = time.monotonic()
        real = ret and frame is not None and not is_signal_loss(frame)
        if real:
            stream_start = now if stream_start is None else stream_start
            if now - stream_start >= 2.0:
                return True
        elif stream_start is not None and now - last_real_t > 0.5:
            stream_start = None            # серия прервалась — заново
        time.sleep(0.02)
    return False
```

### 7.5. Реконнект = release + ПЕРЕСОЗДАНИЕ объекта камеры
Не пытайся «оживить» старый handle — после обрыва/переинициализации
граф DirectShow/GenICam в неизвестном состоянии. Только release + новый
open. При отказе — backoff и повтор.

### 7.6. Индикатор статуса — по флагу, Tkinter только из GUI-потока
Статус камеры хранится как атрибут (пишет поток захвата), GUI-поток
периодически читает и обновляет индикатор при изменении. НИКОГДА не
трогай Tkinter-виджеты из потоков захвата/PLC.
Оверлей «нет сигнала» поверх видео: чёрный экран + надпись — оператор
не должен работать с замороженной картинкой.

### 7.7. Детекция по СВЕЖЕМУ кадру (stale guard)
После потери current_frame содержит ЗАМОРОЖЕННЫЙ кадр. Детекция по нему
даст «правдоподобный» неверный результат (угол уедет в PLC!). Guard перед
любой детекцией (кнопка И триггер):

```python
if not self.camera_connected:
    return error_result
if time.monotonic() - self.last_frame_time > STALE_FRAME_SEC:
    return error_result
```

Для PLC-триггера это ответ DONE=1 + ERROR=1 — PLC-цикл завершится, а не
зависнёт в ожидании.

## 8. ЛОГИ: подавление спама

### 8.1. НЕ вызывай `logging.basicConfig()` в модулях
Остаток basicConfig в импортируемом модуле добавляет свой хендлер на root
— сообщения идут в консоль в обход фильтров и дублируются. Конфигурация
логирования — в одном месте.

### 8.2. Межпоточный лог в GUI — через очередь
Фоновые потоки пишут в `queue.Queue`, GUI-поток забирает по таймеру.
Прямой `root.after()`/доступ к виджетам из потоков — запрещён.

### 8.3. Suppress по шаблонам + уровни для библиотек
```python
logging.getLogger("snap7").setLevel(logging.WARNING)       # сотни строк при недоступном PLC
logging.getLogger("harvesters").setLevel(logging.WARNING)
```

### 8.4. Единственное сообщение на событие
Первое проявление потери — в лог; далее — только при изменении состояния.
Одиночные «шумовые» кадры от мёртвого драйвера не должны сбрасывать
счётчики и спамить.

## 9. СТРУКТУРА КОДА (архитектура потока захвата)

Проверенная архитектура (все баги ниже закрыты ею):

```python
# ФОНОВЫЙ ПОТОК: чтение + реконнект (блокирующие операции — только здесь)
while not stop:
    if cap is None: ...recovery... continue
    ret, frame = cap.read()
    # классификация: real / black / fail
    # real → copy → resize → под lock в current_frame (+version++)
    # loss-переходы: 12 чёрных или read fail → loss_mode
    # в loss_mode: реконнект по backoff

# GUI-ПОТОК: только отображение
# каждые 30 мс: берёт current_frame из-под lock, рендерит по версии кадра
# НИКАКОГО cap.read() и никакого доступа к камере
```

Запрещено:
- `cap.read()` в GUI-потоке (блокирует окно до 2-5 сек при обрыве);
- запись `current_frame` из GUI (кадры вперёд-назад = «разрывание»);
- доступ к Tkinter из фоновых потоков (только флаги + poll в GUI);
- реконнект/пересоздание камеры чаще grace-периода.

## 10. ТЕСТИРОВАНИЕ ЭТИХ ПОДСИСТЕМ

- Fake-клиент snap7: подмена `module.snap7.client.Client` через
  monkeypatch + ручная установка атрибутов клиента. Проверяет цепочки
  write_bit/реконнект/verификацию без железа.
- Дедлок-тест: замер времени вокруг вызова (`time.time()` разница < 5 с)
  — реальный дедлок не бросает исключение.
- Эмулятор + клиент в одном тесте: сервер поднять, canary-проверка
  «наш ли сервер», полный handshake, cleanup. Скип, если порт занят.
- `np.bool_` — возвращай `bool(...)`, `np.True_ is True` даёт False.
- Tkinter-тесты: root видим (без withdraw), фейковые виджеты-заглушки
  (config/place/pack_forget) вместо реальных.
- Глобальные счётчики-реестры — чисти между тестами.
- Тест-парадокс порта 102: интеграционный тест с own-сервером скипай,
  если чужой сервер уже слушает порт.

3. [ ] Тестовый прогон с эмулятором: полный handshake, watchdog мигает,
       OFFLINE реагирует, рестарт эмулятора перезаписывает биты
4. [ ] Живой тест обрыва: выдернуть камеру → потеря за 2-3 сек →
       чёрный экран + блокировка детекции + бесконечный реконнект;
       вернуть → автовосстановление без рестарта
5. [ ] Fail-safe: при старте биты не означают «норма» без подтверждения;
       при краше PC PLC детектит по watchdog
6. [ ] Тесты: полный прогон зелёный
7. [ ] Пароли не в логах, не закоммичены (secrets: env/local file)
8. [ ] Лог: спам подавлен, ключевые события видны

## 12. ТИПОВЫЕ БАГИ (сводка — каждый встречен на практике)

| Симптом | Причина | Решение |
|---------|---------|---------|
| GUI зависает при обрыве камеры | `cap.read()` блокирует до timeout, вызывался в GUI-потоке | поток захвата отдельный; GUI только читает буфер |
| Картинка «разрывается», кадры вперёд-назад | GUI перезаписывал буфер кадров (откат назад) | единственный писатель буфера — поток захвата |
| Реконнект «успешен», но кадры не идут | камера после подачи питания инициализируется; её пересоздавали каждые 2 сек | верификация непрерывного потока ≥2 сек + backoff попыток |
| OFFLINE=1 при отключённой камере | DirectShow отдаёт ЧЁРНЫЕ кадры с ret=True; одиночные шумовые кадры сбрасывали счётчики | детекция чёрных кадров + гистерезис восстановления (3 подряд) |
| PLC читает устаревший угол после рестарта CV | RESULT не обнулён при выключении | RESULT = 0.0 при shutdown |
| Нули перезаписались после обнуления | зомби-поток реконнекта писал после close | `_closed` в клиенте + close_client + обнуление из главного потока |
| OFFLINE дребезжит 0<->1 | счётчик неудач сбрасывался одиночными шумовыми кадрами | гистерезис: восстановление по 3 подряд + порог по времени |
| Два писателя одного байта | RMW-гонка, потерянный бит | домены записи: байт = один писатель |
| Дедлок на реконнекте | threading.Lock + вложенный захват | RLock |
| Подключение отклоняется | PUT/GET запрещён на CPU | включить в TIA Portal |
| PUT/GET не пишет в DB | оптимизированный DB | стандартный (не оптимизированный) блок |
